Ansible MCP Server for Cisco Secure Firewall

Let an AI agent run reviewed Ansible playbooks against Firewall Management Center. The agent never writes automation — it selects from an allowlist a human already merged, and supplies validated variables.

What it does

ToolAccessPurpose
list_playbooksREADThe playbooks this server may run, and which change configuration.
describe_playbookREADPlays, task names, and declared variables. Runs nothing.
check_syntaxREADansible-playbook --syntax-check. Connects to nothing.
dry_run_playbookREAD--check --diff. Reports what would change; issues a confirmation token.
run_playbook_for_realWRITEReal execution. Requires the env gate and a plan-bound token.

Why this, instead of “let the agent write a playbook”

Because a generated playbook is unreviewed automation with production credentials attached. This server inverts the relationship.

Agent writes playbooksThis server
What runsWhatever the model generatedA playbook a human reviewed and merged
Change controlNoneNormal git history and PR review
Blast radiusUnboundedThe allowlist
“What changed?”Read the chat transcriptRead the playbook

The model still adds real value — choosing the right playbook, supplying the right variables, explaining the diff, summarising the recap — without becoming an unreviewed author of production change.

Security model

Agent asks to run "create_network_objects" | v name in allowlist? ------------ no --> rejected | yes v path resolves inside ansible/playbooks? -- no --> rejected | yes v every extra var on the allowlist? -------- no --> rejected | yes v --check --diff (fixed argv, shell=False, timeout enforced) | v plan + confirmation token | [ human reviews ] | v ANSIBLE_MCP_ALLOW_RUN=true AND token authorises this exact plan? | yes | no v v real run rejected
  • Fixed argv, shell=False. Nothing from the model is concatenated into a command string.
  • Allowlisted playbooks. Names are matched against a discovered set, then the resolved path is re-verified to live inside ansible/playbooks/. Traversal such as ../../etc/passwd never resolves.
  • Allowlisted variables. Only a fixed set of lower_snake_case names is accepted. Connection and credential variables (ansible_httpapi_pass, ansible_user, fmc_password) are refused outright — those come from the operator's environment.
  • Variables via file, not argv. Accepted values are written to a temporary JSON file and passed as -e @file, so nothing can be read as a flag and no secret appears in the process table.
  • Filtered child environment. Only an explicit passthrough list reaches the subprocess.
  • Hard timeout with process kill (ANSIBLE_MCP_TIMEOUT, default 600s).
  • Redacted, size-capped output. Vault blobs, passwords, and tokens are stripped before anything reaches the model context.
Read-only by default. The server can only syntax-check and dry-run until ANSIBLE_MCP_ALLOW_RUN=true is set.

1. Configure

Copy .env.example to .env:

ANSIBLE_PROJECT_DIR=/absolute/path/to/fw-automation
ANSIBLE_PLAYBOOK_ALLOWLIST=get_domain,get_network_objects,get_security_zones

FMC_HOST=https://fmc.example.local
FMC_USERNAME=apiuser
FMC_PASSWORD=<export in your shell, or use ansible-vault>
VERIFY_SSL=true

ANSIBLE_MCP_ALLOW_RUN=false
ANSIBLE_MCP_TIMEOUT=600

Install the collection the playbooks use:

ansible-galaxy collection install -r ansible-requirements.yml

Using ansible-vault

ansible-vault create /secure/path/vault.yml    # add: fmc_password: "..."
export ANSIBLE_VAULT_PASSWORD_FILE=/secure/path/vault-pass

2. Run the MCP server

Local Python (stdio)

python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
MCP_TRANSPORT=stdio python -m sfw_mcp_ansible
{
  "mcpServers": {
    "cisco-fmc-ansible": {
      "command": ".venv/bin/python",
      "args": ["-m", "sfw_mcp_ansible"],
      "cwd": "/absolute/path/to/mcp_servers/ansible-mcp",
      "env": {
        "MCP_TRANSPORT": "stdio",

  }
}

Local Python (HTTP)

MCP_TRANSPORT=http MCP_HOST=127.0.0.1 MCP_PORT=8001 python -m sfw_mcp_ansible
No built-in authentication. Front it with a TLS-terminating, authenticating reverse proxy before exposing it beyond localhost.

Docker

docker compose up -d --build

The repository is mounted read-only at /project, so a compromised container cannot rewrite the automation it is allowed to run. Non-root user, read-only root filesystem, all Linux capabilities dropped.

5. Integrating with LLM agents

  1. Register the endpoint (stdio or HTTP).
  2. list_playbooks — the agent learns what it may run and what mutates state.
  3. describe_playbook — explain the intent to the user.
  4. check_syntax, then dry_run_playbook.
  5. Show the dry-run result to a human.
  6. run_playbook_for_real with the plan and token unchanged.
Suggested agent instruction: Always dry-run and show me the would_change_tasks list before running anything for real. If mutates_configuration is true, explicitly ask me to confirm.

Worked example

“Add the new application subnet from the change ticket.”

  1. list_playbooks → create_network_objects (mutates_configuration: true).
  2. describe_playbook → reads its payload from ansible/vars/network_objects.yml.
  3. dry_run_playbook → would_change_tasks: ["Create objects"], plus a token.
  4. Agent shows the diff. Human approves.
  5. run_playbook_for_real(plan, token) → recap changed=1, then “verify in the GUI and deploy”.

Limits

  • --check fidelity depends on the modules involved. Treat a dry run as a strong indication, not a guarantee, and validate against a lab first.
  • The server does not trigger FMC deployments. Review and deploy from FMC.
  • One run at a time per process; there is no job queue.
  • Playbooks are classified as mutating by name prefix (create_, update_, delete_, deploy_, remove_). Name new playbooks accordingly.
